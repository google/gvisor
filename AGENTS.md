# gVisor

### What is gVisor?

gVisor is a userspace kernel used for sandboxing untrusted programs. It is
Linux-like kernel implementation in Go.

NOTE: The project uses [Bazel](https://bazel.build/) as a build system, so paths
starting with `//` refer to the repository root, and `//some/path:some_target`
refers to target `some_target` defined inside `some/path/BUILD`.

gVisor is made of multiple components:

-   The gVisor Sentry is the main component implementing a Linux-like kernel in
    Go. Its implementation is at `//pkg/sentry`.
-   Gofers are I/O proxies for the gVisor Sentry. There are multiple Gofers, but
    an implementation of one is at `//runsc/fsgofer`.
-   `runsc` is a Docker-compatible OCI-compliant container runtime that uses
    gVisor under the hood. It is useful to run Docker images in gVisor.
    Location: `//runsc`.

### Important gVisor subpackages

-   The gVisor "platform" acts as a syscall interception mechanism for sandboxed
    applications, and which is responsible for redirecting control to the gVisor
    sentry for handling the system call. There are multiple platform
    implementations; the name "platform" refers to the abstraction. Location:
    `//pkg/sentry/platform`
-   The gVisor `kernel` package implements the bulk of the kernel logic.
    Location: `//pkg/sentry/kernel`
-   The Linux kernel ABI is redefined as a Go package so that we can use it in
    the gVisor kernel. Location: `//pkg/abi`.
-   The `runsc` CLI is the main entry-point into gVisor for most usage.
-   gVisor may also be used programmatically using a subprocess-like API via
    language bindings with the `sandboxexec` API; see `//sandboxexec`.

### gVisor code conventions

See `//.gemini/styleguide.md` for a general style guide.

In the gVisor codebase, all Go packages use the same package name as the name of
their parent directory. For example:

-   The package at `//pkg/errors/linuxerr` (which is the same as the BUILD
    target `//pkg/errors/linuxerr:linuxerr`) has Go import path
    `gvisor.dev/gvisor/pkg/errors/linuxerr`.
-   The package at `//pkg/sentry/vfs` has Go import path
    `gvisor.dev/gvisor/pkg/sentry/vfs`.
-   This implies that new libraries you may create must be under their own new
    subfolder. For example, if you wish to create a library called `foo` under
    an existing directory `//pkg/bar`, you should create the directory
    `//pkg/bar/foo` and then create a file `//pkg/bar/foo/foo.go` within it. The
    `BUILD` file at `//pkg/bar/foo/BUILD` would contain the `go_library` rule
    with name `foo`, and the `package` line within `//pkg/bar/foo/foo.go` would
    be `package foo`. The import statement for this package in other Go
    libraries would be `gvisor.dev/gvisor/pkg/bar/foo`, and the dependency
    target would be `//pkg/bar/foo`. Other Go source files within
    `//pkg/bar/foo` generally also belong to the same Go package, though it is
    also acceptable to use the `foo_test` package name for test files in the
    same `//pkg/bar/foo` directory, if having a separate package name is
    desirable.
-   gVisor's Bazel rules are wrappers over the usual ones, especially for
    `go_library`, `go_binary`, and `go_test`. They should be imported into
    `BUILD` files from `//tools:defs.bzl`, e.g.
    `load("//tools:defs.bzl", "go_library")` for the `go_library` wrapper. These
    wrapper rules create auto-generated Go source files that are added to the
    source code of each Go package, enabling code generation for Go code that
    gets injected into every package, such as automated serialization. You
    generally do not need to inspect these autogenerated Go source files, but be
    aware that they exist, and that what you see in the repository is not the
    entire picture that the Go compiler actually sees.
-   When writing tests that need to read external files as input, you should use
    the `testutil.FindFile` function defined in `//pkg/test/testutil` with
    import path `gvisor.dev/gvisor/pkg/test/testutil`. It takes in a path as
    argument, which is rooted from the `//` directory. For example, to access
    file `//foo/bar/baz.txt`, you would call
    `testutil.FindFile("foo/bar/baz.txt")`. Every external file that you expect
    to be able to find using `testutil.FindFile` must also be declared as a
    `data` dependency in the `BUILD` target of the `go_test` target you are
    editing. For example, to access file `//foo/bar/baz.txt`, the `go_test`
    BUILD rule would need to have `data = ["//foo/bar:baz.txt"]`. If you want an
    example, look at existing usages of this function to understand how it
    works, e.g. `dumpfilter_test.go` in `//runsc/boot/filter/dumpfilter`.
-   Despite being a bazel project, gVisor uses a Docker-based wrapper over bazel
    using `make`. The `Makefile` defines wrapper rules over `bazel` subcommands,
    which run these commands inside an automatically-managed Docker container.
    This container is useful to smooth over Bazel quirks and version differences
    across machines. For example, building a target is
    `make build TARGETS=//path/to:target`, and running a test is
    `make test TARGETS=//path/to:some_test`.
-   Comments must describe the code as it is for the future codebase readers,
    not for present-time PR reviewers. A comment that talks about a bug that the
    PR at hand fixes is counter-productive, because it leaves behind irrelevant
    historical context that future readers of the codebase should no longer have
    to worry about.
-   Function/struct/field comments should generally not refer to their callers
    (e.g. "Used by", "Useful for"). If this is not already clear from the
    function name or context, then the function name and/or context is the
    problem, and the comment is a band-aid.
-   References to Linux source code must be limited to ABI only. The only
    documentation of Linux behavior that matters is actual behavior as exercised
    by C++ syscall tests.
-   Prose (such as comments, documentation, other markdown files) should mostly
    follow ASD-STE100 Simplified Technical English. Some liberties are expected
    (and welcome in some contexts, such as website/blog post contents), but
    technical content should be crisp, clear, and to-the-point.
-   gVisor is packaged as a fileset at `//:release`, and any consumers of this
    must treat this as an opaque, all-or-nothing set of files to install or set
    up. With narrow exceptions, they should not enumerate the set of files
    within.

### General approach to resolving gVisor issues

#### Modifying gVisor kernel behavior

Use the `gvisor-kernel-development` skill.

NOTE: Do not rely on Linux kernel source code or training knowledge when
implementing syscall behavior. Instead, test your assumptions by writing syscall
tests to verify Linux behavior from a black-box perspective.

#### Security first

All changes are reviewed for security. gVisor's design and architecture ensures
that a Sentry compromise, however unlikely, is still tightly contained.
Nonetheless, any changes to the Sentry are very security-sensitive and must be
reviewed carefully to avoid introducing new escalation vectors. See
`SECURITY.md` for various aspects of gVisor security.

#### Compatibility in practice

gVisor aims to match broad Linux-like behavior, but this is a moving target and
some incompatibilities matter more than others in practice. If there exists no
popular real-world application that runs into the compatibility problem that a
PR is addressing, the PR review will be de-prioritized against those that do
have popular real-world applications.

The pecking order, from most important to least, with compatibility tag:

-   `COMPATIBILITY:REGRESSION-GVISOR`: Regressions in real-world application
    compatibility of a previously-supported application, due to past changes in
    gVisor.
-   `COMPATIBILITY:REGRESSION-APP`: Regressions in real-world application
    compatibility of a previously-supported application, due to changes/updates
    by the application.
-   `COMPATIBILITY:UPCOMING-KERNEL`: Incompatibilities not yet encountered, but
    known to later be encountered due to an upcoming change in the Linux kernel.
-   `COMPATIBILITY:NEW-APP`: Incompatibilities encountered in real-world
    applications that never worked in gVisor before, in their default
    configuration/use-case.
-   `COMPATIBILITY:NEW-APP-CONFIG`: Incompatibilities encountered in real-world
    applications that never worked in gVisor before, in a specific non-default
    configuration/use-case.
-   `COMPATIBILITY:PREVENTIVE-APP`: Syscall-test-only change that verifies a
    piece of **working** gVisor compatibility that isn't yet covered by syscall
    tests, which is known to be relied upon by a real-world application.
-   `COMPATIBILITY:UPCOMING-APP`: Incompatibilities not yet encountered, but
    known to later be encountered due to an upcoming change in an application
    that currently works in gVisor.
-   `COMPATIBILITY:SYNTHETIC`: Incompatibilities exercisable only via syscall
    tests, which no known real-world application encounters.

Note that only applications that are publicly usable count in the above rating
scale. In other words, if the only known application of a specific Linux-like
behavior is something a gVisor reviewer can't test, then that application does
not exist for the purpose of the compatibility tag.

Compatibility changes without a compatibility tag will be rejected.

#### Performance sensitivity

As a kernel, gVisor performance matters almost as much as security. As such, any
change that may impact performance is required to come with benchmark
measurements to measure its benefit and to avoid regressions.

The following code is particularly performance-sensitive:

-   The system call hot path: entry and dispatch in `pkg/sentry/kernel`
    (`task_run.go`, `task_syscall.go`), the handlers in
    `pkg/sentry/syscalls/linux`, and the layers that copy data to and from
    application memory (`pkg/usermem`, `pkg/safemem`, `pkg/safecopy`,
    `pkg/marshal`).
-   Platform code (`pkg/sentry/platform`, `pkg/ring0`).
-   Serialization code (`pkg/state`).
-   Sandbox startup (`runsc/boot`, `runsc/container`, `runsc/sandbox`).
-   Netstack (`pkg/tcpip`).
-   Checkpoint/restore (`pkg/state`, `pkg/sentry/state`).
-   File I/O (`pkg/sentry/vfs`, `pkg/sentry/fsimpl`).
-   Memory management (`pkg/sentry/mm`, `pkg/sentry/pgalloc`).
-   Inter-process communication with the gofer (`pkg/lisafs`, `runsc/fsgofer`).
-   Go `init()` functions that run on every binary startup.

Load the `gvisor-performance` skill whenever any of these paths show up, or when
a change has any possibility of performance implications. Test-only changes do
not have performance implications.

#### Filesystem checkpoint versioning

Filesystem checkpoints (`//pkg/sentry/fscheckpoint`, `//pkg/sentry/pgalloc`,
`//pkg/sentry/fsimpl/tmpfs`, `//runsc/boot`) target 12 months of backward
compatibility: `runsc` at `HEAD` must be able to restore checkpoints saved up to
12 months ago.

-   Increment `Manifest.version` (set in `pkg/sentry/kernel/fscheckpoint.go` and
    checked in `runsc/boot/fscheckpoint.go`) or
    `MemoryFileMetadataProto.version` (set and checked in
    `pkg/sentry/pgalloc/save_restore.go`) whenever a proto or on-disk format
    change (including `multitar` regular-file encodings in
    `pkg/sentry/fsimpl/tmpfs/fscheckpoint.go`) requires restore logic to
    distinguish old and new checkpoints, or would cause an older `runsc` binary
    (which silently ignores unknown proto3 fields) to misinterpret a newer
    checkpoint.
-   Keep restore support for all checkpoint versions released within the past 12
    months when bumping a version number.

## Git / GitHub / PR Guidelines

Before sending PRs, check the following:

-   Compatibility fixes must come with a compatibility tag (see "Compatibility
    in practice" section), along with an explanation for this tag.
-   Syscall behavior must be verified to match Linux behavior by way of syscall
    tests, not Go tests.
-   Everything must build; use `make build TARGETS=...` building affected paths.
-   Relevant tests must pass; use `make test TARGETS=...` or
    `make syscall-tests TARGETS=...` as appropriate.
-   All PRs must pass `make lint` and `make lint-cc`.
-   Performance-sensitive changes must come with benchmark data, with
    statistically-significant figures. See "Performance sensitivity" section.
-   Website changes should come with before/after screenshots (use
    `make website-server` to start an HTTP server serving the site locally).
-   The change must go through adversarial review, unless the human told you to
    skip it (see "Adversarial review" section).
-   Test-only changes that improve stability/flakiness are very much welcome.

### Buildkite CI results

CI runs on Buildkite. The main pipeline is
`https://buildkite.com/gvisor/pipeline`; other pipelines, such as `release`, are
in the same `gvisor` organization. The public pipelines need no Buildkite token.
Use `tools/buildkite/buildkite.py` to read build results; do not scrape the
Buildkite web pages.

`tools/buildkite/buildkite.py failed BUILD [REGEX]` prints the failed jobs of a
build as JSON. `BUILD` is one of:

-   a build URL (any build or job link);
-   a GitHub PR URL: the newest build on the PR branch. Compare its `commit`
    with the PR head commit. PRs from forks have no build in the main pipeline.
    A PR URL uses 1 of the 60 GitHub API requests per hour;
-   a build number;
-   a branch name: the newest build on that branch.

`--pipeline NAME` (or `ORG/NAME`) selects the pipeline for all builds except
build URLs. The default is the main pipeline.

-   Each job has an entry for each failed attempt. If Buildkite retried the
    attempt, `retry` is the outcome of the next attempt: `passed` (the failure
    is a possible flake), `failed` (the next entry), `pending` (not finished
    yet) or `canceled`.
-   `annotated_targets` are the Bazel targets that failed, timed out, or were
    flaky (passed when Bazel ran them again) in the job, with the URL of their
    `test.log`. `unattributed_targets` are such targets in a job that the tool
    cannot identify.
-   `REGEX` is case-insensitive and matches the job name or an annotated target.
    `--soft-failed` adds the soft-failed jobs, which do not fail the build.
-   `--logs` downloads the log of each failed attempt whose retry did not
    finish, and adds the lines that tell why the job failed: `log.error`,
    `log.failure_lines` and `log.excerpt`, the end of the command output. The
    failure lines include the Bazel results, the failed Go tests and Google Test
    tests with their messages, and compiler errors. Each annotated target gets
    its Bazel `status`, such as `FAILED`, `TIMEOUT` or `FLAKY`. `--all-attempts`
    also downloads the logs of attempts whose retry finished.

`tools/buildkite/buildkite.py log JOB_URL [--tail N]` prints a job log as plain
text, without terminal control codes. `JOB_URL` is the `url` of a job.

Some failures come from the CI infrastructure, not from the change. For example,
the job has exit status `-1` because Buildkite lost the agent. A job with
`state: timed_out` (also exit status `-1`) ran longer than its time limit, which
can also happen when the change causes a job to stop responding.

## Adversarial review

Run adversarial review on each change to this repository that you report to the
human, whether you or a sub-agent wrote it, when the change is complete: it
builds, you have run its tests and lint (report any failures, and anything you
could not run), and you are about to hand it back to the human, whatever words
you use to describe it. Unless the human said that the change will not go
upstream, assume that it is. Only the agent that reports to the human handles
adversarial review. Reviewer sub-agents do not.

Do not run adversarial review:

-   On intermediate edits, while the implementation is still in progress.
-   On changes that the human said are not meant to go upstream, such as
    exploratory prototypes, debug instrumentation, or local benchmark scripts.
-   When the human explicitly tells you to skip it.

Scale the number of sub-agents to the size and risk of the change (a one-line
fix needs fewer reviewers than a new Sentry feature).

The applicable set of sub-agents depends on the type of change. Consider these:

-   Run a **security agent** looking for ways to break the security or bypass
    the checks you may have added: bad permission checks, race conditions, user
    namespace considerations, ability for a compromised Sentry to do more than
    it used to be able to do before the change, etc. Must be present for any
    Sentry, Gofer, `runsc`, or seccomp change.
-   Run a **security hardening agent** looking for ways to increase the security
    of your change further: usages of less-error-prone Linux system calls (e.g.
    FD-based over path-based file syscalls), specific flags in syscall that
    reduce the likelihood of the syscall being used for something it's not
    intended to do (e.g. `O_NOFOLLOW`, `O_PATH`, `O_CLOEXEC`, `O_NOCTTY`,
    `RESOLVE_*`, etc), tighter seccomp filter rules on the Sentry, etc. Must be
    present for any Sentry, Gofer, `runsc`, or seccomp change.
-   Run a **performance regression agent** looking for potential performance
    regressions, e.g. new dependency bloating the binary or adding `init()`
    functions, or adding a system call in the startup hot path causing an RCU
    stall, etc. Must be present for any Sentry, Gofer, or `runsc` change, or
    changes to any of the performance-sensitive paths described above.
-   Run a **performance optimization agent** looking for ways to optimize your
    change's performance, such as by avoiding allocations, adding `+checkescape`
    annotations, shortening functions where possible to make them inlineable,
    using newer higher-performance Go runtime features, using more efficient
    syscall patterns, etc. Must be present for any Sentry, Gofer, or `runsc`
    change, or changes to any of the performance-sensitive paths described
    above.
-   Run a **testing exhaustivity agent** looking for missing test cases, e.g.
    adding more cases for black-box C++ syscall tests to more exhaustively cover
    expected behavior, or more ways to invoke `runsc` or gVisor in new ways that
    your change adds complexity for, etc. Must be present for any change other
    than test-only changes, build-infra-only changes or documentation-only
    changes.
-   Run a **correctness agent** looking for ways in which this change is
    incorrect: logic bugs, code not matching comments, not all scenarios
    handled, etc. Must be present for any change.
-   Run a **stylistic agent** looking for ways in which the change violates the
    project's code conventions: comments, lint, code references, commit message
    description, etc. Must be present for any change.
-   Run a **documentation agent** looking for any existing documentation that
    your change invalidates, and report it. Note however that documentation
    agents tend to be very prone to suggesting documentation that does not need
    to exist; ensure any agent-suggested documentation changes are scoped to
    strictly fixing actively-invalid documentation, not to adding a litany of
    caveats to existing still-generally-correct documentation. If in doubt, ask
    the human if it is worth it.
-   Run a **free-range agent** which is given the task to find what other
    sub-agents to spawn beyond the ones from the set above that are worth
    considering for the change at hand. Must be present for any change.
-   Run a **catch-all agent** that is given no particular objective in mind
    other than to review the change in general. Must be present for any change.

Adversarial review works best when sub-agents are initially given the
absolute-minimum context (e.g. only where to find the change and the reviewer's
objective), such that they do not anchor on assumptions you or your human
operator may have implicitly made along the way. Your role as the coordinator is
to act on the sub-agents' findings, once all sub-agents in the round have
reported or failed. Rerun a failed sub-agent once; if it fails again, list it as
not run. If a finding is immediately and obviously applicable (e.g. a typo, or a
bug you can confirm), then implement it. Otherwise, determine whether the
finding is worth acting upon or not by arguing about it with the sub-agent. For
example, if a finding is out of the initial change's intended
scope/intentions/constraints, reveal more of the change's context until you come
to an agreement with the sub-agent. If a finding repeats what another sub-agent
or a previous round of adversarial review already brought up, summarize those
former arguments to determine whether they still hold. Do not reject a finding
unless the sub-agent agrees with your reasoning for doing so. If you still
disagree after three exchanges, list the finding as disputed in your report and
let the human decide. If your eventual conclusion is that the finding should be
acted upon, then implement it.

Review sub-agents may run tests or perform read-only operations without asking
you for permission; do not tell them otherwise. If they need to modify code in
order to verify their assumptions or run additional one-off tests, let them make
those changes only in their own git worktree (never in the main tree) with the
change under review applied to it (check out or apply the full change under
review, including untracked files and commits not yet upstream; do not commit or
stage anything in the main tree), so that they don't step on each other's toes.
If a sub-agent wants to run a benchmark, they must coordinate with you in order
to do so when the machine is quiet (i.e. no other sub-agent may run a build,
test, or benchmark at the same time). If a sub-agent asks to verify something
that a previous round already verified, give it that result instead. When a
sub-agent is done with its worktree and any argument about its findings has
ended, run `make bazel-shutdown` in it, and then delete it.

After you apply adversarial review findings, run build/tests/lint again. If any
finding you applied may also result in performance changes, run benchmarks as
well.

You should stop adversarial review once sub-agents stop finding new issues and
only nitpick or rehash previous findings that have already been rejected or
listed as disputed. Follow-up rounds of adversarial review should still start
with no more context than the first round, though you may include minimal
context to avoid rehashing findings if the same finding comes up in at least two
consecutive rounds of review. If a tenth consecutive round for the same request
from the human (a new request resets the count; your own follow-up work does
not) still leads you to change code or test logic, stop and ask the human how to
proceed.

After you are done with these rounds of review, if they caused significant
changes beyond your initial implementation or the human's initial request, or if
any findings remain disputed, or if any sub-agent failed and was not run,
summarize the review and its outcome: which sub-agents you ran, which sub-agents
you did **not** run and why, which findings remain disputed, which findings you
rejected and why, and which findings you fixed and why.
